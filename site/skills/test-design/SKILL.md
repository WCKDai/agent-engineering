# Test design

A test is code the project maintains forever. It earns its place by protecting an observable
contract that a credible regression would break and no existing test already guards. Agents tend
to write too many tests, at the wrong layer, held together by sleeps.

## Activate when

- Adding or extending tests for a feature or fix.
- A test needs a timeout, a retry, a sleep or a polling loop to pass.
- A suite is slow or flaky, or a review says "this test does not prove anything".
- Code reads durable state, retries requests or handles partial failure.

## Inputs and assumptions

- The repository's test layers (unit, integration, end-to-end), their commands and conventions.
- Existing tests for the area: read them before writing a new one.
- The behavior under test, stated as an observable contract.

## Outputs

- The smallest set of tests, at the lowest layer that fails on the unfixed code.
- For each new test: the contract it protects, the regression that would break it, and why no
  existing test catches that regression (in the PR description, not as a comment).
- The kind of evidence the change needs if a test is the wrong tool (see step 6).

## Permissions and restrictions

Never make a test pass by raising a timeout, adding a retry, adding `sleep`, polling, or skipping
it on one platform. Never assert on wall-clock time differences. Do not add a test-only parameter,
export, flag or global to production code where the repository forbids test seams; where it does
not, prefer a real product option or the existing dependency-injection or test-layer mechanism. A
failing test is never skipped in code; the only way to set one aside is the quarantine in
failure-investigator (owner, expiry, reported unverified). Do not loosen a golden file, fixture or
expected value to make a test pass; that is a behavior change. Recorded states and fixtures are
synthetic or sanitized: no production or customer data.

## Workflow

1. Answer three questions before writing a regression or behavior test: which observable
   contract does this protect, which credible regression would make it fail, and why does no
   existing test catch it? If you cannot answer all three, do not add the test. Characterization
   tests that pin current behavior before a refactor (safe-refactor) are exempt: they pass before
   and after by design.
2. Extend before you add: a new row in an existing table test beats a new test. One contract has
   one owning test.
3. Place it at the lowest layer that fails on the current code. Do not test what the type system
   already guarantees, mirror mock calls back, or snapshot static markup.
4. Make it deterministic: seed randomness and wait on the event or condition itself, not on time.
   Control time in this order: the test framework's fake clock or test scheduler (for example fake
   timers or a test clock), then an existing product option or injected dependency that shortens
   the duration, then a new option only where the repository allows test seams. If none is
   available, stop and ask the owner; do not fall back to sleeping.
5. For durable state, keep a corpus of states recorded from older versions (generated by test
   runs, or sanitized; never customer data) and replay them on every change. Keep fixtures that
   must be rejected too, so a check that became too permissive fails.
6. For failure handling, inject the fault (request failed, response lost after the work was done,
   storage call failed) and assert that the injected fault actually fired, so a refactor that
   bypasses the path fails the test instead of passing it.
7. Match evidence to the change: logic and protocol bugs get a failing test first; a purely visual
   change gets before/after captures; a server-only fix gets a test plus a short runtime transcript.
8. The mental-revert check (the one place Creed defines it): for each new regression or behavior
   test, ask whether it would still pass if the implementation were reverted. If yes, it proves
   nothing; fix or delete it. Characterization tests are exempt.

## Verification

- Each new regression or behavior test was seen failing on the code without the change (see
  regression-guardian); characterization tests pass on both sides.
- The test file contains no new sleeps, retries, raised timeouts or unreasoned skips (`rg` the diff).
- The new tests pass in at least 20 consecutive runs with no retries, for example a shell loop over
  `cargo nextest run --retries 0 <filter>` or `pytest <test>`; `pytest --count`
  only if pytest-repeat is installed. A failure rate is measured as in failure-investigator.
- Replay and fault-injection tests fail when their fixture or fault is removed.

## Failure and escalation

- A test is flaky: measure the failure rate over repeated runs and look for the commit that
  introduced it; do not call one green rerun proof. Quarantine only through failure-investigator.
- The only way to test is through a seam the repository forbids: stop and propose a design change
  to the owner.
- No layer can observe the contract: state that the behavior is unverified rather than adding a
  test that asserts the implementation.

## Done when

Every new regression or behavior test has a stated contract and regression, sits at the lowest
failing layer, is deterministic, was seen failing before the change, and the suite contains no new
timing crutches or in-code skips.
